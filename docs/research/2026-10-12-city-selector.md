# City selector — v3 vs v4 prior art

Commander ask: "City Selector — autocomplete like in v3/v4 (check which solution is more elegant)."

## v3 (`~/Projects/wedance-v3`, Nuxt 2 + Firestore)

Four overlapping components, all Google Places:

| Component | UX | Value |
|---|---|---|
| `TInput/TInputCity.vue` | Fake select → opens a `TPopup` with a search box. Empty query lists active Firestore `cities`; typing calls `AutocompleteService.getPlacePredictions({types:['(cities)']})`. "Anywhere" row. Auto-locate via `navigator.geolocation` + reverse geocoding (`response[5]` — a magic index). | City **name** string |
| `TInputLocationSelect.vue` | Same popup, "Locate me" row, hard-coded 4 German cities as the empty list. | Location object |
| `TInputLocation.vue` | Read-only box + "Change" button → popup, "Use my current position". | Location object |
| `TInputPlace.vue` | `t-rich-select` (vue-tailwind) with async `fetchOptions`; empty query shows the current city profile. | Google **place_id** |

Side effects inside the input: picking a city geocodes the place and **writes a new Firestore `cities` / `profiles` doc** (`status: 'requested'`). Key: the Firebase browser API key reused for Maps JS.

- Good: "Locate me" (geolocation), empty-state list of known cities, "Anywhere".
- Not elegant: four copies of the same logic; a modal for a single field (two taps, focus moves away); no keyboard support (div `@click` rows, no ARIA); every keystroke is a paid Places request with no debounce; the input mutates the database; brittle `response[5]` reverse-geocode index.

## v4 (`~/Projects/wedance-v4`, Nuxt 3 + shadcn-vue + Prisma)

One component: `components/inputs/CityInput.vue` = shadcn `Popover` + `SearchableDropdown` (button trigger with map-pin, search box inside the popover, "Anywhere" button). Data: `composables/useCities.ts` → Google `AutocompleteService` once the query has ≥2 chars. Server `server/utils/city.ts::addCity` geocodes the place_id later and creates a Prisma `City` row with slug collision handling (`region-locality`). Value `{ id: place_id, name }`. `googleMapsApiKey` is empty in `nuxt.config.ts` (env-supplied). Used in ArtistsGrid, EventsList, VenuesView, GroupsGrid, PostEditor.

- Good: single composable + single component; design-system popover; ≥2-char threshold; DB write moved server-side.
- Not elegant: still a button-then-search-box popover (two steps, `role="combobox"` on a button whose popup holds another `role="combobox"` with an empty `aria-controls`); no arrow-key navigation; no debounce; no geolocation; needs a paid Maps key; `SearchableDropdown` re-filters Google results client-side by substring, which can hide valid predictions ("Munich, Germany" vs query "München").

## Verdict

**v4 is the more elegant** — one composable, one component, popover from the design system, persistence moved to the server. v3 had the nicer *features* (known-cities empty state, locate-me) but buried them in four copy-pasted modals that write to the DB.

2026 takes v4's shape (one composable + one ui component) but drops two things neither needed:

1. **The popover-with-a-button.** The text field itself is the combobox (ARIA 1.2 editable combobox, list autocomplete): one tap, type, arrow, Enter. Same surface as `Input` (`controlVariants`), works inside `Field`.
2. **Google Places.** 2026 has no Maps/Places key in `.env` (checked names only), and it doesn't need one: it already knows its cities.

## How 2026 stores cities

- `dancers.city`, `profiles.city`, `events.city`, `rideshares.origin_city`, gigs `location` — **free-text name strings**. `profiles.city_slug` / `events.city_slug` carry the slug for `/cities/<slug>`.
- `server/data/city-images.json` — 389 cities keyed by slug with `country` and `altNames` (München, Múnich, Мюнхен…), generated by `scripts/fetch-city-images.mjs`.
- `/api/cities` — SSR list of cities with visible profiles, counts + image metadata.

So the v-model is the **city name string** (no shape migration), and suggestions come from a new `/api/city-options` that merges profile cities (real names, ranked by community size) with the image catalogue (country + alternative spellings; image-only cities get a name from a matching alt spelling, else title-cased slug). ~470 rows (~25 KB gzipped), fetched once on first focus, filtered client-side (accent/case-insensitive, alt names, word-prefix, country) with a 120 ms debounce — no request per keystroke, no key, no cost.

## Deliberately not carried over

- **Locate me / use my position** — needs reverse geocoding (Google or similar) and the catalogue has no coordinates. Revisit if `city-images.json` gains lat/lng (nearest-city lookup would then be free).
- **"Anywhere"** — v3/v4 used the input as a *filter*; 2026's filter UIs don't need it. Clearing the field (Esc twice) gives an empty value.
- **Writing new cities from the input** — free text is saved as typed in the owning record; nothing is created from a keystroke.
